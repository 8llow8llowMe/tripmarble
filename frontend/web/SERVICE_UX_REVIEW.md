# TripMarble Service UX Review

작성일: 2026-04-23

## 0. 문서 목적

이 문서는 TripMarble Web의 현재 UX를 기능 단위로 다시 검토하고, 이후 리디자인 작업이 스타일 보정에 머무르지 않도록 서비스 수준의 기준을 정리하기 위한 리뷰 문서다.

이 문서는 다음 문서와 역할이 다르다.

- `frontend/web/DESIGN.md`: 시각 언어와 디자인 레퍼런스
- `frontend/web/REDESIGN_TASKS.md`: 디자인 토큰, 공통 UI, 스타일 시스템 작업표
- `frontend/web/SERVICE_UX_REVIEW.md`: 사용자 흐름, 화면 역할, 기능별 UX 문제와 재설계 기준

문서 간 충돌이 생기면 아래 우선순위를 따른다.

1. 사용자 흐름과 서비스 역할
2. 화면별 UX 구조
3. 시각 스타일 가이드

즉, `DESIGN.md`의 Apple 스타일은 참고 기준일 뿐이고, TripMarble의 실제 서비스 경험을 해치면 그대로 따르지 않는다.

## 1. 현재 판단 요약

현재 수정사항은 전부 롤백할 대상은 아니다. 공통 스타일 기반 작업은 유지 가치가 높고, 실제로 다시 설계가 필요한 부분은 서비스 경험을 결정하는 화면들이다.

현재 상태를 한 줄로 정리하면 다음과 같다.

- 장점: 토큰, 공통 컴포넌트, 카드/모달/폼 규칙이 정리되면서 화면 간 시각적 일관성은 좋아졌다.
- 문제: 홈, 여행지 탐색, 게임 생성, 게임 플레이, 캔버스 보드의 핵심 사용자 흐름은 여전히 분산되어 있다.
- 결론: 전체 롤백보다 `기반 유지 + 핵심 화면 재기획 후 재작업`이 맞다.

## 2. 왜 지금 결과가 "스타일만 통일된 느낌"인지

현재 `REDESIGN_TASKS.md`는 목표와 작업 순서 자체가 토큰, 공통 UI, 레이아웃 shell, 카드 통합, 페이지별 리디자인 순으로 잡혀 있다. 이 접근은 시각 시스템 정리에는 적합하지만, 아래 항목은 충분히 다루지 못한다.

- 사용자가 서비스에 들어왔을 때 첫 행동이 무엇인지
- 여행지 탐색과 게임 생성이 어떻게 이어지는지
- 플레이 중 현재 상태를 2초 안에 이해할 수 있는지
- 보드 캔버스가 장식이 아니라 조작 가능한 플레이 표면인지
- 미션 인증과 리뷰 작성이 플레이 루프 안에서 자연스럽게 이어지는지

즉, 현재 문서는 "어떻게 보이게 할 것인가"에는 답했지만 "왜 이 화면이 존재하고 어떤 행동을 유도해야 하는가"에는 답하지 못한다.

## 3. 서비스 정의를 다시 고정해야 하는 이유

TripMarble은 현재 아래 세 가지 성격이 동시에 섞여 있다.

- 여행지 탐색 서비스
- 여행 계획 보조 서비스
- 여행 미션형 보드게임 서비스

세 성격이 모두 필요하지만, 현재 화면은 이 세 역할을 같은 강도로 동시에 말하고 있다. 그 결과 홈은 연출이 강하고, 여행지 상세는 정보가 많고, 게임 화면은 규칙은 있지만 진행 안내가 약하다.

이 문서에서는 TripMarble의 핵심 가치를 다음과 같이 정의한다.

`TripMarble은 여행지를 탐색하고, 그 여행을 게임 루프로 전환하고, 실제 방문 기록을 미션과 리뷰로 남기는 서비스다.`

이 정의를 기준으로 서비스는 세 단계로 나뉜다.

1. 여행 전: 지역 탐색, 장소 비교, 게임 생성
2. 여행 중: 보드 진행, 미션 수행, 리뷰 인증
3. 여행 후: 기록 회고, 리뷰 확인, 게임 종료

이후 모든 화면은 이 세 단계 중 어디에 속하는지 명확해야 한다.

## 5. 기능별 상세 리뷰

### 5.1 Home

대상 파일:

- `src/app/page.tsx`
- `src/entities/home/ui/home-dice/HomeDice.tsx`
- `src/entities/home/ui/home-dice/HomeDice.module.scss`
- `src/entities/home/ui/polaroid-stack/**`

현재 상태:

- 3D 주사위와 보드 이미지, 폴라로이드 스택을 활용한 연출이 강하다.
- CTA는 `게임 만들기`, `여행지 보기` 두 가지다.
- 사용자는 스크롤을 해야만 지역 탐색의 맥락을 더 보게 된다.

현재 문제:

- 홈 첫 화면이 "무엇을 해야 하는 서비스인지"보다 "어떤 연출을 보여주는지"에 더 많은 비중을 둔다.
- 로그인한 사용자의 현재 게임, 이어서 플레이, 최근 지역 탐색 같은 실제 진입점이 없다.
- 폴라로이드와 보드가 시각적으로는 흥미롭지만, 서비스의 핵심 행동을 더 빠르게 이해시키지는 못한다.

재설계 방향:

- 홈은 브랜드 연출 페이지가 아니라 `서비스 진입 허브`가 되어야 한다.
- 첫 화면에서 최소 아래 세 가지 중 하나는 즉시 보여야 한다.
- `새 게임 만들기`
- `이어하기`
- `지역 탐색 시작`
- 3D와 보드 연출은 유지하더라도 첫 액션과 서비스 구조를 가리지 않는 범위에서만 사용한다.
- 지역 탐색 카드는 "예쁜 이미지"보다 `이 지역으로 게임을 시작할 수 있다`는 연결이 명확해야 한다.

완료 기준:

- 첫 화면만 보고도 서비스가 `여행 탐색 + 게임 진행 + 방문 기록`의 구조임을 이해할 수 있다.
- 로그인 사용자는 "내가 지금 무엇을 이어서 해야 하는지"를 홈에서 바로 알 수 있다.
- 비로그인 사용자도 회원가입보다 먼저 서비스 체험 경로를 볼 수 있다.

### 5.2 Spots List / Regional Discovery

대상 파일:

- `src/app/(spots)/spots/page.tsx`
- `src/app/(spots)/spots/SpotsList.module.scss`
- `src/shared/ui/common/HorizontalList/**`

현재 상태:

- 지역 목록과 추천 여행지를 수평 리스트로 보여준다.
- 시각적으로는 정리되었지만 정보 밀도와 행동 유도는 약하다.

현재 문제:

- 지역 목록과 추천 여행지 목록이 `왜 함께 존재하는지`가 약하다.
- 추천 여행지를 보고 나서 무엇을 해야 하는지 명확하지 않다.
- 리스트 UI가 많지만, 사용자의 비교 행위나 선택 결정을 돕는 구조는 약하다.

재설계 방향:

- 지역 리스트 화면의 역할을 `여행 시작점 선택`으로 고정한다.
- 지역 카드에는 최소 아래 정보 중 일부가 필요하다.
- 대표 이미지
- 지역명
- 대표 분위기 또는 추천 테마
- 게임 시작 또는 둘러보기 진입
- 추천 여행지는 독립 섹션이 아니라 `지금 많이 보는 장소`, `게임 만들기 좋은 지역`, `사진이 많은 지역`처럼 맥락이 있어야 한다.

완료 기준:

- 지역 목록 화면에서 사용자의 다음 행동이 `지역 상세로 이동` 또는 `게임 생성으로 연결` 중 하나로 분명해진다.

### 5.3 Spots Detail / Map-Heavy Exploration

대상 파일:

- `src/app/(spots)/spots/[id]/page.tsx`
- `src/app/(spots)/spots/[id]/SpotListPanel.tsx`
- `src/app/(spots)/spots/[id]/SpotDetailPanel.tsx`
- `src/app/(spots)/spots/[id]/Spot.module.scss`
- `src/shared/ui/map/KakaoMap.tsx`

현재 상태:

- 지도, 리스트 패널, 상세 패널 구조는 어느 정도 나뉘었다.
- 모바일에서는 bottom sheet 구조가 들어가 있다.
- 리뷰 요약과 상세 정보도 한 화면 안에서 확인할 수 있다.

현재 문제:

- 기능은 많지만 이 화면의 우선 목적이 `탐색`, `비교`, `게임 시작`, `리뷰 보기` 중 무엇인지 약하다.
- 상세 패널과 지도 패널이 병렬로 존재하지만, 선택과 비교 흐름은 아직 정교하지 않다.
- 모바일 sheet는 열리고 닫히는 구조는 있으나 단계적 확장이나 행동 중심 구조는 약하다.
- 필터는 존재하지만 실제 탐색 전략을 도와주는 정도는 아직 낮다.

재설계 방향:

- 이 화면의 주 역할을 `지역 내 장소 비교와 게임 출발점 선택`으로 명확히 둔다.
- 지도는 배경이 아니라 비교 보조 도구가 되어야 한다.
- 리스트는 선택 후보군, 상세 패널은 선택 확정 정보, CTA는 `이 장소 중심으로 게임 만들기` 또는 `리뷰 남기기`로 명확히 나눠야 한다.
- 모바일에서는 sheet가 단순 상세창이 아니라 `요약 -> 상세 -> 액션`의 단계로 올라와야 한다.
- 필터는 단순 content type 나열보다 `가볼 만한 곳`, `사진 미션에 좋은 곳`, `리뷰 많은 곳`처럼 사용자 의도와 연결되는 방향을 검토한다.

완료 기준:

- 사용자가 지도와 리스트 사이에서 헤매지 않고 한 장소를 비교하고 선택할 수 있다.
- 선택된 장소가 게임 시작과 어떻게 이어지는지 분명하다.
- 모바일에서도 상세 패널이 지나치게 답답하지 않고 액션 CTA가 분명하다.

### 5.4 Search

대상 파일:

- `src/app/search/page.tsx`
- `src/app/search/Search.module.scss`

현재 상태:

- 자동완성 검색과 추천 지역 리스트가 있다.

현재 문제:

- 검색 페이지와 지역 탐색 페이지의 역할이 겹친다.
- 검색은 정확히 일치하는 경우에만 이동하는데, 사용자는 이를 자연스럽게 기대하지 않는다.
- 검색 후 도착하는 목적지가 지역 상세인지 여행지 상세인지도 강하게 구분되지 않는다.

재설계 방향:

- 검색 페이지의 역할을 `빠른 진입`으로 분명히 한다.
- 지역 검색인지 장소 검색인지 명시해야 한다.
- 자동완성 결과는 단순 텍스트가 아니라 `유형`, `지역`, `다음 행동`이 함께 보이는 구조가 좋다.
- 검색 결과 선택 이후 사용자가 `탐색 계속`, `게임 만들기`, `리뷰 보기` 중 무엇을 할지 자연스럽게 이어져야 한다.

완료 기준:

- 검색은 탐색 페이지의 중복 복제본이 아니라 `직접 진입 도구`로 기능한다.

### 5.5 Create Game

대상 파일:

- `src/features/game/create-game/ui/CreateGameModal/index.tsx`
- `src/features/game/create-game/ui/CreateGameModal/CreateGameModal.module.scss`
- `src/features/game/create-game/ui/CreateGameModal/steps/**`

현재 상태:

- 제목, 지역, 테마, 날짜, 난이도 순으로 값을 입력받는다.
- 모달 구조와 진행 바는 정리되어 있다.

현재 문제:

- 사용자가 지금 "입력"하고 있는지 "여행 게임을 설계"하고 있는지 감각이 약하다.
- 난이도 선택이 보드 크기, 이동 템포, 플레이 길이와 어떻게 연결되는지 직관적이지 않다.
- 마지막에 요약 확인 단계가 없어 생성 직전 기대값을 점검하기 어렵다.
- 특정 지역 상세에서 진입했을 때 맥락이 얼마나 이어지는지 약하다.

재설계 방향:

- Create Game은 폼이 아니라 `여행 게임 세팅 플로우`가 되어야 한다.
- 지역에서 진입한 경우 해당 지역이 기본 선택되고, 사용자는 이를 확인만 하도록 흐름을 줄일 수 있어야 한다.
- 난이도는 라벨만이 아니라 `추천 일정`, `보드 규모`, `플레이 감각`까지 함께 보여야 한다.
- 마지막 단계에는 `게임 요약`과 `시작 후 무엇이 가능한지`를 짧게 보여주는 확인 단계가 필요하다.

완료 기준:

- 생성 완료 전에 사용자가 만들 게임의 성격을 분명히 이해한다.
- 입력 단계 수는 유지하더라도 심리적으로는 더 짧게 느껴져야 한다.

현재 문제:

- 사용자가 "내가 지금 해야 할 게임"보다 "모든 게임 카드"를 먼저 보게 된다.

- 예를 들어 진행 중은 `현재 단계`, `다음 행동`, `마지막 활동 시간`이 중요하고, 종료된 게임은 `완료 요약`이 중요하다.

완료 기준:

- 사용자가 목록에 들어오면 가장 먼저 계속 플레이해야 할 대상을 찾을 수 있다.

- `src/entities/games/ui/game-play/GamePlay.tsx`

현재 상태:

현재 문제:

- 현재 턴 상태, 도착 결과, 미션 가능 여부가 여러 위치에 흩어져 있다.
- 보드와 하단 버튼의 관계는 있지만, 사용자의 현재 목표가 강하게 드러나지 않는다.
- `타임라인`과 `게임 방법`이 같은 레벨의 하단 탭을 차지하면서 실제 플레이보다 보조 정보가 전면에 나온다.
- 종료 액션은 존재하지만 전체 플레이 구조 안에서 맥락상 다소 외따로 있다.

재설계 방향:

- 플레이 화면은 `현재 상태 -> 보드 -> 다음 행동 -> 기록` 순으로 재구성해야 한다.
- 사용자에게 항상 아래 네 가지 중 하나가 보여야 한다.
- 지금 내 위치
- 지금 해야 할 행동
- 이번 턴 상태
- 이번 행동이 끝나면 무엇이 열리는지
- 타임라인은 메인 플레이 표면 아래의 보조 영역이나 서랍형 구조로 내려도 된다.
- 게임 방법은 첫 방문 툴팁 또는 접힌 도움말 영역으로 낮추는 편이 낫다.

완료 기준:

- 사용자가 화면 진입 후 2초 안에 다음 행동을 알 수 있다.
- 주사위, 이동, 도착, 미션 인증이 하나의 연속된 흐름처럼 느껴진다.

현재 상태:

- 보드 셀 렌더링, 클릭, 드래그, 말 이동, 방문 마커, 주사위 오버레이가 구현되어 있다.
- 시각적으로는 보드게임 느낌이 살아 있다.

현재 문제:

- 캔버스는 렌더링 중심으로 설계되어 있어 현재 사용 가능한 액션을 안내하지 않는다.
- 드래그는 되지만 사용자가 드래그해야 하는 이유와 범위를 배우기 어렵다.
- 현재 위치, 선택된 칸, 도착 예정 칸, 수행 완료 칸이 UX적으로 체계화되어 있지 않다.
- 주사위 연출 뒤 실제 이동까지 지연이 있고, 이 대기 시간이 플레이 템포를 끊을 수 있다.
- 캔버스는 접근성 측면에서 보조 정보 없이 단독 조작 표면이 되기 어렵다.

재설계 방향:

- 보드 캔버스는 "예쁜 보드"가 아니라 `플레이 스테이지`가 되어야 한다.
- 최소 아래 상태가 시각적으로 분명해야 한다.
- 현재 위치
- 이번 턴 도착 칸
- 이미 방문한 칸
- 실패 또는 스킵된 칸
- 눌러서 정보 확인 가능한 칸
- 보드 주변에는 최소 아래 보조 조작이 필요하다.
- 현재 위치로 이동
- 전체 보드 맞춤
- 확대 또는 축소
- 상태 범례
- 캔버스만으로 모든 의미를 전달하려 하지 말고, 동기화된 DOM 정보 패널을 함께 유지해야 한다.
- `prefers-reduced-motion`에서는 주사위 및 말 이동 대기 시간을 줄이거나 건너뛰어야 한다.

완료 기준:

- 사용자가 보드를 보자마자 현재 위치와 다음 행동을 알 수 있다.
- 캔버스가 조작 표면으로 느껴지고, 필요한 조작은 별도 보조 컨트롤로도 접근 가능하다.
- 모션이 길어도 답답하지 않거나, 줄일 수 있는 옵션이 있다.

현재 문제:

- 사진 첨부와 리뷰 입력은 미션 성공의 일부라는 감각을 더 줘야 한다.

완료 기준:

- 모달에 들어오면 지금 이 장소에서 할 수 있는 행동이 분명하다.
- 정보 확인과 인증 제출이 불필요하게 분리되어 느껴지지 않는다.

## 6. 앞으로 작업할 때 지켜야 할 공통 원칙

### 6.1 한 화면에 하나의 1차 행동만 둔다

같은 수준의 CTA가 여러 개 나오면 사용자는 판단을 미룬다. 각 화면은 반드시 아래 중 하나를 1차 행동으로 가져야 한다.

- 탐색 시작
- 게임 생성
- 플레이 이어하기
- 미션 인증
- 리뷰 남기기

### 6.2 화면의 역할을 먼저 정하고 스타일을 입힌다

다음 질문에 답하지 못하면 CSS부터 손대지 않는다.

- 이 화면의 주 역할은 무엇인가
- 사용자가 가장 먼저 해야 할 행동은 무엇인가
- 보조 정보는 어디까지 전면에 나와야 하는가
- 모바일에서 같은 목적을 어떻게 유지할 것인가

### 6.3 캔버스는 항상 DOM 보조 구조를 가진다

보드 캔버스는 시각적 중심이 될 수 있지만, 상태 설명과 액션은 DOM 기반 보조 구조를 유지해야 한다.

- 현재 상태 배지
- 선택된 칸 정보
- 기본 조작 버튼
- 접근 가능한 행동 경로

### 6.4 도움말은 기본 정보가 아니라 보조 정보다

게임 방법, 범례, 추가 설명은 사용자가 막혔을 때 찾는 정보여야 한다. 기본 플레이 흐름보다 먼저 보이면 안 된다.

### 6.5 디자인 레퍼런스는 제품 경험을 대체하지 않는다

Apple 스타일은 시각적 참고일 뿐이다. TripMarble의 핵심은 여행 정보와 게임 루프 결합이므로, 과도한 연출이 기능 이해를 늦추면 구조를 바꿔야 한다.

## 8. 실제 작업 전에 체크할 리뷰 템플릿

이후 어떤 기능을 수정하더라도 아래 템플릿을 채우고 시작한다.

### 8.1 기능 리뷰 템플릿

- 기능명:
- 주 사용자 단계: 여행 전 / 여행 중 / 여행 후
- 현재 주 행동:
- 현재 문제:
- 유지할 요소:
- 다시 설계할 요소:
- 관련 파일:
- 모바일 핵심 시나리오:
- 접근성 또는 상태 이슈:
- 완료 기준:

### 8.2 화면 착수 전 질문

- 사용자는 이 화면에 왜 들어왔는가
- 가장 먼저 알아야 할 정보는 무엇인가
- 첫 CTA는 무엇인가
- 보조 정보는 접어둘 수 있는가
- 에러, 빈 상태, 로딩, 완료 상태가 모두 정의되어 있는가
- 모션이 없어도 이해 가능한가

### 8.3 한 번에 수정할 작업 단위

이후 실제 구현은 기능 단위를 너무 크게 잡지 않는다. 한 번의 작업은 아래 중 하나만 해결하는 수준으로 자른다.

- 홈 진입 구조 정리
- 지역 탐색에서 게임 생성 연결 정리
- 게임 생성 요약 단계 추가
- 게임 플레이 상단 상태 바 정리
- 보드 캔버스 조작 보조 컨트롤 추가
- 미션 모달의 정보/인증 흐름 정리

한 작업 안에서 여러 흐름을 동시에 바꾸면, 무엇이 좋아졌고 무엇이 깨졌는지 판단이 어려워진다.

### 8.4 화면 작업 산출물 규칙

각 기능 수정은 아래 산출물을 남기는 것을 기본으로 한다.

- 수정 목적 1문장
- 변경 파일 목록
- 유지한 요소와 바꾼 요소 구분
- 주요 상태 목록
- 모바일 기준 동작 요약
- QA 체크 결과

주요 상태 목록에는 최소 아래 항목이 포함되어야 한다.

- 기본 상태
- 로딩 상태
- 빈 상태
- 에러 상태
- 완료 또는 성공 상태
- 비활성 또는 잠금 상태

QA 체크 결과에는 최소 아래 항목이 포함되어야 한다.

- 360px / 390px / 834px / 1440px 확인
- keyboard focus 확인
- reduced motion 영향 확인
- 텍스트 잘림 또는 겹침 확인
- primary CTA가 즉시 보이는지 확인

## 9. 이번 리뷰 문서 기준 결론

지금 필요한 것은 스타일 보정이 아니라 서비스 재정렬이다.

따라서 다음 작업은 아래 순서를 따른다.

1. 이 문서를 기준으로 핵심 화면의 역할을 다시 확정한다.
